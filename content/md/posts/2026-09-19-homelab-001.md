# Starting Off

Homelabs are really popular nowadays, and it's always nice to experiment with new technologies, learn how things work, and test different services. With a homelab, you can have your own private drive, a private Git server, or even a private LLM running for your own projects.

The only thing you really need to start a homelab is a computer. It can be an old PC, a laptop, a Raspberry Pi, or even another small device capable of running a server. For this series, my main homelab server will be this one:

![Dell 3080 PC](/img/homelab/dell-optiplex-3080.webp){width=200px; height=400px}

As you can see, it's an old [Dell OptiPlex 3080 Micro](https://www.dell.com/en-us/shop/computadores-all-in-ones-e-workstations/optiplex-3080-micro/spd/optiplex-3080-micro). There's no specific reason for choosing this computer. For me, the main advantage is that it's small and can fit almost anywhere in my apartment.

## Installing an Operating System

In order to make this computer work as a server, we first need to choose an operating system. The idea is to access the server only through SSH. Since we want to save resources and don't need a graphical interface, there's no reason to install a desktop environment.

For now, we just need a free operating system that can run our services and allow us to connect through SSH. To achieve this, I think the easiest option is [Ubuntu Server](https://ubuntu.com/download/server).

Ubuntu Server already has everything we need for this project. Since this guide isn't focused on installing Ubuntu Server, I'll recommend the [*Install Ubuntu Server - Full Setup Guide*](https://www.youtube.com/watch?v=K2m52F0S2w8) video from TechHut. It's a very well-made and beginner-friendly video that can guide you through the entire installation process.

**IMPORTANT:** During the system installation, don't forget to install and enable the **OpenSSH Server**. Without it, you won't be able to connect to your server through SSH.

# Challenges

Okay, now that you have your server up and running, you might be thinking:

> "How can I access my services from outside my home network?"

Or:

> "How are we going to manage the security of the server?"

Before answering these questions, we need to understand how computer networks work, and more specifically, how a typical **home network** works.

## How Does a Home Network Work?

When you sign up with an **ISP (Internet Service Provider)**, your ISP provides you with an Internet connection. Depending on the setup, you may receive a router or a modem/router combination.

Your router connects your local network to the Internet and typically receives a **public IP address** from your ISP.

For example:

```text
Public IP: 200.100.50.25
```

Every website or Internet service you access communicates with the Internet using your connection's public IP address. That's the basic idea.

You might then think:

> "If I know my public IP address, can't I just connect directly to my server?"

That's a reasonable assumption. However, there are a few important things we need to understand first.

## NAT (Network Address Translation)

The first important concept is **NAT**, which stands for **Network Address Translation**. NAT is a mechanism usually handled by your router that allows multiple devices inside your private network to share a single public IP address when accessing the Internet.

For example, your home network might look like this:

```text
Laptop        192.168.0.10
Phone         192.168.0.11
Server        192.168.0.14
                    │
                    ▼
                 Router
                    │
                    ▼
              200.100.50.25
                    │
                    ▼
                Internet
```

The devices inside your home network use **private IP addresses**, such as `192.168.0.10` or `192.168.0.14`. These private addresses are not directly reachable from the public Internet. The router sits between your private network and the Internet, translating the private IP addresses of your devices into the public IP address provided by your ISP.

Internally, the router keeps track of connections using information such as IP addresses and ports, allowing it to know where an Internet response should be sent.

## Port Forwarding

This creates another important question:

**If the router knows how to send responses back to my devices, how can an external connection reach my server in the first place?**

This is where **port forwarding** comes in. Port forwarding allows you to create a rule on your router that says something like:

> "If my public IP receives a connection on port 3000, forward that connection to my server at 192.168.0.14 on port 3000."

The topology would then look something like this:

```text
Internet
    │
    │ 200.100.50.25:3000
    ▼
 Router
    │
    │ Port Forwarding
    │
    ▼
192.168.0.14:3000
    │
    ▼
Ubuntu Server
```

This is one of the traditional ways of hosting a service from a home network. However, whether you can actually configure port forwarding depends on your router and, more importantly, on how your ISP provides your Internet connection. Some ISPs also use **CGNAT**, which can make traditional port forwarding impossible.

## Why Don't We Have a Fixed Public IP?

Another important detail is that having a public IP doesn't necessarily mean having a **fixed public IP**. Your ISP may assign you a dynamic public IP address.

For example, today your connection might have:

```text
200.100.50.25
```

and tomorrow it could change to:

```text
200.100.50.83
```

Your Internet connection would continue to work normally, but anyone trying to reach a service hosted at your house using the old IP address would no longer reach your network. This is one of the problems you have to consider when hosting services from home.

There are solutions such as **Dynamic DNS (DDNS)** that can automatically update a domain name whenever your public IP changes. However, there is another problem that can make things even more complicated: **CGNAT**.

## CGNAT (Carrier-Grade NAT)

NAT is something that usually happens inside your local network and is managed by your router. However, some ISPs also use another layer of NAT called **Carrier-Grade NAT (CGNAT)**. CGNAT allows an ISP to place multiple customers behind a shared public IP address.

The topology can look like this:

```text
Ubuntu Server
192.168.0.14
    │
    ▼
  Router
    │
    ▼
 ISP CGNAT
    │
    ▼
 Internet
```

In this situation, your router may not actually have a public IP address. Instead, it may receive an address from the ISP's private/shared address space and then communicate with the Internet through the ISP's CGNAT infrastructure. This creates a major problem for hosting services at home. Even if you configure port forwarding on your own router, an incoming connection from the Internet still has to pass through the ISP's CGNAT before reaching your router. Since you don't control that NAT layer, you generally cannot configure a port forwarding rule there. As a result, **traditional inbound connections to your home network may not be possible when you're behind CGNAT**. And this is where things start to get interesting.

If we want to access our homelab from anywhere, but we don't have a fixed public IP, we may be behind CGNAT, and we don't necessarily want to expose our home network directly to the Internet, **how can we access our server remotely?** That's where technologies such as **VPNs, WireGuard, and Tailscale** come into play.
